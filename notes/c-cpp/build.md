---
1. 预处理阶段

首先来看预处理阶段。预处理器相当于一个文本处理器，负责嵌入 `#include` 头文件内容、展开由 `#define` 定义的宏、移除注释并解析条件编译指令，最终生成一个不包含任何预处理指令的纯净源代码文件。

可以在 Linux 系统中使用 `g++` 得到预处理后的代码；在 macOS 中更推荐使用 `clang++`，因为 `g++` 在 macOS 中是 `clang++` 的别名。其中，`-E` 选项告诉编译器进行预处理，`E` 是 `expand` 的首字母，对应预处理的功能，即将头文件和宏展开。正因为预处理的核心任务之一是查找并包含文件，所以该阶段最常见的错误便是“No such file or directory”。

---
2. 编译阶段

其次是编译阶段。该阶段编译器会对预处理阶段得到的纯净源代码文件进行词法、语法和语义分析；在检查无误后，将代码优化并翻译成特定目标平台的汇编代码。

可以通过 `g++` 命令的 `-S` 选项得到这一阶段的产物。可以选择从上一步的 `.i` 文件生成汇编代码，也可以直接从源码生成汇编代码。编译阶段的常见错误是各种语法和语义错误，比如变量命名中的不合法字符、缺少分号等。

---
3. 汇编阶段

之后是汇编阶段。汇编器将上一阶段生成的汇编代码翻译成机器码，即 CPU 能够直接执行的二进制指令，并将这些指令和相关数据打包成一种标准格式的文件，即目标文件。目标文件通常以 `.o` 作为后缀。

使用 `-c` 选项进行汇编。这里的 `c` 是 compile 的缩写。你可能会觉得奇怪：既然是在 assembly 阶段，为什么命令选项却是 compile 的首字母 `c` 呢？这是一个历史遗留的术语习惯。在早期的 C 语言工具链中，狭义的 compile 只指从源代码到汇编代码 `.s` 的过程；广义的 compile 则指从源代码到目标文件的整个过程，包含预处理、狭义编译、汇编这三个步骤。这里的 `-c` 选项取的是广义 compile 的含义。

注意，这里的二进制目标文件不再是文本文件，因此不能直接查看其内容。但是，可以通过反汇编指令 `objdump`，将 `.o` 文件中的二进制机器码翻译回人类可读的汇编代码。可以看到，相比于 `.s` 的汇编代码，这个反汇编 `.o` 出来的代码是带有具体地址偏移的二进制机器码，丢失了所有原始注释和汇编伪指令。

由于汇编阶段是对编译后的 `.s` 文件的直接翻译，因此通常不会引入新的源代码语义错误。因为如果有这类错误，编译器就一定会在上一个阶段暴露出来。不过，汇编器本身仍可能报告与汇编语法、符号、重定位或目标文件格式相关的错误。

---
4. 链接阶段
汇编之后是链接阶段。

---
4.1 静态库链接

链接器将目标文件与所需的静态库进行合并；通过符号解析，将函数调用与其实际定义匹配；并通过地址重定位，为代码和数据分配最终的内存地址；最终生成一个单一、完整的可执行文件，例如 Linux 中的 .elf 或 Windows 中的 .exe。

注意：在链接时，链接器将被用到的代码完整地从静态库中复制，并嵌入到最终的可执行文件中。这会生成一个体积较大、但完全自包含的程序；它在运行时不依赖任何外部库文件。

静态链接时，最常见的错误是：链接器在提供的所有 `.o` 文件和 `.a` 文件中找不到某个函数或变量的实现体。这会直接导致 `undefined symbol` 或 `undefined reference` 报错。

此外，当手动使用 `g++` 构建工程时，一个常见的陷阱是库的链接顺序。由于链接器通常是单向扫描依赖的，如果库 A 依赖库 B，那么库 B 必须出现在库 A 的后面。例如，`g++ -lA -lB` 是正确的顺序；反之，如果写成 `g++ -lB -lA`，链接器在处理库 A 时，就无法解析其对库 B 的依赖，从而抛出 `undefined reference` 错误。

现在来演示一下具体的静态库链接实操。代码实例为 Static demo 一：其中主函数 `main.cpp` 依赖于 `my_add` 和 `my_multiply` 这两个功能模块，而这两个功能模块自身是相互独立的。需要将这两个功能模块打包为静态库，再将 `main` 函数和这个打包后的静态库进行链接。

首先，使用 `-c` 选项将功能模块和主程序 `main.cpp` 这三个源代码文件都编译成目标文件。接着，使用 `ar` 归档器命令将这些 `.o` 文件打包成一个静态库。静态库的标准命名规范是 `libname.a`，这里命名为 `libmymath.a`。这里的 `rcs` 是三个选项组合在了一起：其中 `r`（replace）表示替换库中已有的同名 `.o` 文件；`c`（create）表示如果库不存在，就创建它；`s`（symbol index）表示创建一个符号索引，这能加快后续的链接速度。

你可能会好奇：为什么 `ar` 命令的选项参数没有 `-` 符号？这是因为 `ar` 命令属于上古遗留工具，在 POSIX 和 GNU 规范统一天下之前就已经存在，是“活化石”；而大一统之后的现代命令工具，如 `g++`，都会有 `-` 作为命令选项的前缀。

然后进行静态链接，将 `.o` 和 `.a` 得到可执行文件。链接器会读取 `main.o`，发现它需要 `add` 和 `multiply` 函数；然后链接器会去 `libmymath.a` 中查找这两个函数，将它们的实现代码复制出来，并嵌入到最终的可执行体 `my_program` 中。现在目录中会生成可执行文件 `my_program`，且可以得到正确的运行结果。

最后，来证明一下前面所说的：静态链接得到的可执行文件是静态库的完整复制和嵌入。只需要证明 `my_program` 执行体在运行时不再需要构建过程中产生的静态库 `libmymath.a`，当然也不需要任何 `.o` 文件。现在当前目录会有这些文件：`my_program` 可执行文件、`libmymath.a` 静态库文件、`.o` 后缀的目标文件，以及 `.cpp` 和 `.h` 源码。删除所有的构建产物，即静态库 `.a` 和目标文件 `.o`；删除后的当前目录中只剩下源码 `.cpp`、`.h` 以及最终的可执行文件 `my_program`。程序依然可以正确运行，这可以证明 `my_program` 在运行时没有以任何方式去查找 `libmymath.a` 或任何 `.o` 文件，因为它所需要的所有代码已经被完整地复制和内嵌到执行体内部了。

有兴趣的同学可以自行尝试一下“库 A 依赖库 B”的这种带有依赖的静态库链接案例。代码 `static demo two` 和操作命令讲解文稿，我会放在我的 GitHub 仓库中，这里不再赘述。如果你发现命令参数顺序和依赖的顺序无关，比如 `g++ libb.a liba.a` 也能成功链接，那么这是现代链接器优化的结果；但是在一些版本较旧的 Linux 发行版或嵌入式开发中，不遵循正确的依赖顺序，就会导致链接失败。

---
5. 运行阶段 & 4.2 动态库链接

构建期间的阶段已经全部完成，现在我们来到了运行时的加载阶段。

在程序运行时，操作系统的动态加载器会解析可执行文件中的引用标记；这是链接器在构建时留在可执行文件中的一个占位符，表明程序需要一个来自外部动态库的函数。随后，加载器会在系统中查找所需的动态库，例如 .so、.dll，并将它们加载到进程的内存空间中。

注意，动态库在构建时被编译为位置无关代码（Position Independent Code，PIC），这样它们才能被安全地加载到内存中的任何可用地址，以实现多进程共享。如果内存中尚无此库，则加载；如果已有，则多个程序将共享同一份代码副本。

加载完成后，加载器会执行“运行时的符号解析”，将程序中的函数调用存根链接到库在内存中的实际地址；以及“地址重定向”，即将程序中对函数的模糊调用修正为指向库代码在内存中的确切物理位置。最终，在内存中构建一个完整的程序镜像，准备交由 CPU 执行。

动态加载时的常见错误是：在运行时，操作系统的动态加载器无法在它的标准搜索路径中找到动态库文件，因为你可能把动态库放在了其他地方。

可以看到，运行时的动态加载得以实现，其前提是构建时链接阶段的准备：链接器必须先在可执行文件中写入引用标记，加载器才能在运行时解析这些标记并加载动态库。

---
4.2 动态库链接

现在来演示一下具体的动态库链接实操。

首先，编译源代码为 `.o` 目标文件。这一步与静态库类似，但必须添加 `-fPIC` 标志。其中的 PIC 就是前面介绍的 Position Independent Code，即位置无关代码。它告诉编译器：构建阶段生成的代码不要依赖于它被加载到内存中的绝对地址。这是动态库必须的要求，因为它在运行时可能被加载到任何可用的内存位置。具体细节可参见我的“内存布局”视频中的 ASLR。

接着，由目标文件 `.o` 创建动态库。这一步不再是 `ar` 命令，而是使用 `g++` 的 `-shared` 标志。动态库名称的标准命名规范是 `lib<name>.<后缀>`。注意，动态库的后缀是平台相关的：macOS 为 `.dylib`，Linux 为 `.so`，Windows 为 `.dll`。现在目录中会生成动态库 `libmymath.dylib`，这里是 macOS 平台。

然后，编译主程序得到 `main.o`。这一步和静态库完全相同。

最后，链接 `.o` 文件和动态库。这一步只是在可执行文件中记录引用。命令中的 `-L.` 告诉链接器在当前目录搜索库；`-lmymath` 则是告诉链接器链接标准命名为 `libmymath` 的动态库。这里的小写 `-l` 表示跨平台的快捷方式。动态库比静态库更需要规范命名，因为静态库在不同平台都是 `.a` 后缀，而动态库则具有不同的后缀。这种平台无关性是自动化构建系统（如 CMake）的基础。

现在目录中会生成可执行体 `my_program_dynamic`，且可以正确运行。注意，此时的可执行文件 `my_program_dynamic` 不包含 `add` 和 `multiply` 的具体实现代码，只是包含一个“便条”，写着：运行时需要加载 `libmymath.dylib`。

现在我们来证明它其实是在运行时才被加载的。删掉当前目录的 `libmymath.dylib`，再次运行 `my_program_dynamic` 就会失败报错，因为运行时的加载阶段找不到动态库。

也可以在 macOS 上使用 `otool -L my_program_dynamic` 查看某个执行体依赖的动态库；Linux 上则对应 `ldd my_program_dynamic`，其中 `ldd` 是 list dynamic dependencies 的缩写。

## 具体命令

### 构建流程

```bash
# 预处理: 文本替换, cpp->ii
g++ -E foo.cpp -o foo.ii

# 编译为汇编: 语义分析, ii->s
g++ -S foo.ii -o foo.s

# 汇编为目标文件: 翻译为机器码, s->o
g++ -c foo.s -o foo.o

# 链接为可执行文件
g++ foo.o -o app
```

### 静态库与动态库的生成与链接

```bash
# main.cpp 依赖 foo.cpp

# 静态库: libfoo.a
g++ -c foo.cpp -o foo.o
ar rcs libfoo.a foo.o  # 创建静态库
g++ main.o -L. -lfoo -o app  # 链接静态库

# 动态库

# Linux: libfoo.so
g++ -fPIC -c foo.cpp -o foo.o  # 编译成位置无关目标文件
g++ -shared foo.o -o libfoo.so  # 生成共享对象
g++ main.o -L. -lfoo -o app  # 链接动态库

# MacOS: libfoo.dylib
clang++ -fPIC -c foo.cpp -o foo.o
clang++ -dynamiclib foo.o -o libfoo.dylib
clang++ main.o -L. -lfoo -o app

# Windows MinGW: foo.dll
g++ -shared foo.o -o foo.dll -Wl,--out-implib,libfoo.dll.a
g++ main.o -L. -lfoo -o app.exe
```
